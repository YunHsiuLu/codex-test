# Chapter 10：錯誤作為資料與純核心／副作用邊界

## 學習目標

設計可區分原因的錯誤型別；理解 ? 的傳遞規則；把解析、計算與 I/O 責任分開。

## 理論與設計理由

panic 適合指出某些程式內部預期被破壞的情況，不適合把每個使用者輸入錯誤都當成程式崩潰。Result 把成功與失敗列為介面的一部分，呼叫者可決定重試、記錄、顯示或終止。比起 Err("錯了")，具名 enum 可以穩定區分欄位數、轉換、非有限值與領域限制。

? 不是忽略錯誤。對 Result 而言，它在成功時取得內容，失敗時提早回傳；必要時透過相容的 From 轉換錯誤型別。map_err 則明確改寫錯誤表示。責任仍存在，只是傳遞路徑比層層 match 短。

把 parse_record(&str) 寫成不直接讀檔、不印訊息的函式，讓同一個邏輯能被測試、終端機或其他 UI 使用。最外層負責取得文字與顯示錯誤，內層負責判斷文字是否符合資料規格。這種邊界讓測試可以固定輸入，不需模擬使用者鍵盤或檔案權限。

錯誤分類也代表驗證順序。本題先檢查兩欄，再轉數字，再檢查有限性，最後檢查正時間。若某行同時違反多個條件，回傳先遇到的錯誤。API 應交代這點，測試才不會把實作細節誤當隨機結果。本練習只是兩欄逗號分隔格式，不支援引號內逗號等完整 CSV 規則；應明確說出格式範圍。

## 推理實驗

畫出「讀檔 → 字串 → parse_record → Result → 外層顯示」的資料流。對 abc,0 預測回傳哪一個錯誤並解釋驗證順序。比較回傳 Result 與函式內直接 println! 的可重用性。

## 實作規格

完成 parse_record；接受正負位移，但時間須為有限正數。剛好兩欄，忽略欄位兩端空白。不得用 unwrap 逃避外部資料的轉換失敗。

起始檔：`examples/lab10.rs`。先閱讀測試，再修改函式。

```sh
cargo test -p rust-advanced-course --example lab10
cargo run -p rust-advanced-course --example lab10
```

起始程式中的 `todo!()` 可編譯，但執行或相關測試會 panic，這是刻意保留的待完成工作；通過編譯不代表通過規格。

## 終端機自動驗收

完成作答後執行：

```sh
cargo run -p rust-advanced-course -- run 10
```

此命令自動編譯學生程式並執行至少十項獨立具名的函式契約檢查（清單見 `TEST_CASES.md`），不需手動輸入測試值。第十二章另有多組標準輸入／輸出與退出碼案例。驗收在暫存檔附加測試，不會修改你的程式或使用參考答案替換作答；失敗退出碼為１。起始程式中的 `todo!()` 會使驗收失敗。

需要自行輸入、觀察輸出或附加檔案路徑時，使用 `cargo run -p rust-advanced-course -- manual 10`；原本的 `cargo test -p rust-advanced-course --example lab10` 仍可執行檔案內測試。自動驗收有逾時限制，但不是執行不受信任程式的安全沙盒；有限測試也無法代替設計推理、複雜度分析與個別口頭說明。

## 驗收與設計說明

每一種錯誤變體至少一個測試。函式本身不執行 I/O。成本 O(n)；目前參考解法使用 Vec 保存兩欄，延伸可用 iterator 檢查第三欄並移除該配置。

提交修改後的程式、測試結果及一頁設計說明。設計說明必須回答：不變量是什麼？錯誤如何表達？時間／額外空間成本是多少？你的測試還沒有涵蓋什麼？

## 提示

用 parse::<f64>().map_err(...)?；建立錯誤變體後，再依固定順序檢查。
