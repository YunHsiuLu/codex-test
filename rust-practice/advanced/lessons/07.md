# Chapter 07：資料建模、型別不變量與模組邊界

## 學習目標

以建構函式維護有效狀態；理解欄位可見性與封裝限制；區分型別安全與領域正確性。

## 理論與設計理由

若任意 f64 都能當作時間，呼叫每個計算函式時就要重新問它是否為零、負數、NaN 或無限大。建立 Seconds 新型別，並只透過驗證過的建構函式產生值，可以把「有限正數」變成該型別的不變量。後續函式接收 Seconds 時，便能依賴這個約定。

這個設計仍需封裝。若把內部欄位公開，使用者可以直接造出 Seconds(-1.0)，建構函式的保證就被繞過。Rust 的私有欄位以模組為界，同一個模組內仍能直接存取；要對外建立可靠 API，型別與修改途徑應放進受控模組，不能只在檔案開頭加 private 的想像。

另一方面，型別不變量越強，使用成本也可能越高。若某個領域允許零時間作為初始狀態，硬套嚴格正數型別反而不合需求。先定義領域，再選資料模型；不是每個 f64 都要包裝，也不是包裝之後就能忘記單位。

列舉型別還能表達彼此互斥的狀態，例如 Loading、Ready(Data)、Failed(Error)。相比三個可任意組合的 bool，它減少了「已成功又已失敗」這類沒有意義的組合。這是利用型別的可表示狀態引導設計。能用型別排除的錯誤，通常比散落的註解更容易維護，但數值公式是否正確仍需要規格與測試。

## 推理實驗

列出用三個 bool 表示 Loading／Ready／Failed 時的八種組合，指出哪些沒有領域意義。再設計 enum，使可表示狀態只包含允許的情況。比較 Seconds 的建構驗證與每次計算都驗證的成本及責任。

## 實作規格

完成 Seconds::new，只接受有限正數；get 以借用取得數值，不提供無檢查的 setter。延伸：將 Seconds 移入獨立模組，證明外部不能直接構造無效欄位。

起始檔：`examples/lab07.rs`。先閱讀測試，再修改函式。

```sh
cargo test -p rust-advanced-course --example lab07
cargo run -p rust-advanced-course --example lab07
```

起始程式中的 `todo!()` 可編譯，但執行或相關測試會 panic，這是刻意保留的待完成工作；通過編譯不代表通過規格。

## 驗收與設計說明

正常值與四種錯誤值通過。設計說明必須明確承認：目前同模組仍能直接構造欄位；延伸模組化才建立對外邊界。說明 Seconds 並不自動防止把其他單位換算錯。

提交修改後的程式、測試結果及一頁設計說明。設計說明必須回答：不變量是什麼？錯誤如何表達？時間／額外空間成本是多少？你的測試還沒有涵蓋什麼？
