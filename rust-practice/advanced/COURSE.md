# Rust Advanced Course

這是一門以 Rust 學習程式設計、系統資源與可靠介面設計的進階課程。重點是從規格推理、解釋設計取捨，再以程式與測試提供證據；不是只背語法或修到編譯成功。

## 前置知識與操作環境

先完成 [Rust Beginner Course](../beginner/README.md)，能獨立使用變數、判斷、迴圈、函式、基本所有權、Vec、Option、Result 與測試。熟悉終端機、Cargo 與編輯器；不要求 C++ 背景。需要支援 Rust 2024 edition 的工具鏈（Rust １．８５ 以上），建議使用目前 stable。安裝見 [跨平台說明](../beginner/README.md)。所有命令除另註外由 rust-practice workspace 根目錄（含 [workspace] 的 Cargo.toml）執行。

# Chapter 01：從問題規格到函式契約

## 學習目標

區分數學問題、機器可表示範圍與 API 契約；從規格推導邊界案例；理解 Option 所表達的資訊。

## 理論與設計理由

程式設計先決定「什麼算正確」，才決定程式怎麼寫。以 ０ 到 n 的整數總和為例，數學定義是 T(n)＝n(n＋1)／2，但回傳型別若是 u32，就不可能容納任意大的結果。寫下公式不等於已解決機器上的問題。

函式契約可分為前置條件與後置條件。本題 n 可為任何 u32，不要求呼叫者先檢查；若數學結果可由 u32 表示，必須回傳 Some(精確結果)，否則回傳 None。這使函式對每一個合法型別輸入都有明確語意。None 在這裡只代表範圍不足，不是總和為零；Some(0) 才是數值零。

先乘再除可能在中間步驟溢位，即使最終結果其實裝得下。n 與 n＋1 至少有一個是偶數，因此可先把偶數除以二，再做 checked_mul。這是從代數性質改寫運算順序，而不是碰到 panic 才猜補丁。也要避免先計算 n＋1 導致 u32::MAX 溢位；可以依 n 的奇偶性安排運算。

一般整數運算的溢位行為受到編譯設定影響，不應把 debug 的 panic 或 release 的結果當作 API 契約。checked 運算讓範圍限制變成明確的資料。與改用較大型別相比，checked 適合把「不在目標型別範圍」表達給呼叫者；較大型別則可能簡化中間計算。兩者都必須對照規格，而不是只追求少寫幾行。

測試提供有限案例的證據，推導則說明對整個輸入範圍為何成立。兩者互補：代數推導可能寫錯程式，測試也可能漏掉最大的輸入。

## 推理實驗

先手算 n＝0、1、65536。比較「先乘後除」與「先除偶數後乘」的中間值，說明為什麼 65536 的最終總和可表示，直接相乘卻可能超過 u32。再指出 u32::MAX 應在哪個步驟回報 None。

## 實作規格

完成 triangular。禁止用浮點數近似整數結果；必須處理全部 u32 範圍。先寫契約，再以代數推導決定實作。

# Chapter 02：有限表示、浮點誤差與數值演算法

## 學習目標

辨識精度與範圍的差異；用極端輸入反駁不安全公式；區分數學恆等式與浮點運算等價。

## 理論與設計理由

f64 使用有限的位元表示數值，因此只能表示有限個值。許多十進位小數不能精確轉為有限長的二進位表示。數值很大時，相鄰可表示數之間的間距也會變大；這是相對精度的限制，不是程式輸出位數太少。

浮點運算不遵守所有實數代數規則。先加再減可能失去小量，交換括號可能改變結果。比較浮點結果時常使用絕對誤差與相對誤差：絕對誤差適合靠近零的量，相對誤差適合跨不同數量級的量。容許誤差應由問題與量測精度決定，不能把 1e-9 當作萬用魔法數。NaN 亦不能用一般相等比較辨認，必須用 is_nan 或 is_finite 等語意檢查。

平均兩個數的公式 (a＋b)／2 在兩數都接近 f64::MAX 時，中間和會變成無限大。改成 a＋(b－a)／2 又會在異號極值時讓差溢位。本題依正負號分支：同號數的差不會出現這種極端放大，異號數的和則可避免同號相加的溢位。這個推導針對有限數，不能直接延伸到 NaN 或無限大。

這個演算法旨在減少可避免的中間溢位，不承諾每個次正規數與捨入情況都得到理論上最理想的結果。例如極微小差值除二可能下溢。數值軟體要先寫清楚誤差與可接受輸入，不能只說「使用浮點數就支援實數」。實驗也不能取代對輸入範圍的分析。

## 推理實驗

執行以下程式，預測並解釋兩個結果：

```rust
let small = (1e16_f64 + 1.0) - 1e16_f64;
assert_eq!(small, 0.0);
assert!(((f64::MAX + f64::MAX) / 2.0).is_infinite());
```

畫出兩個運算樹，標註數學上正確的中間值與機器實際保存的值。

## 實作規格

完成 midpoint：只接受兩個有限 f64，回傳有限的近似中點；輸入 NaN 或無限大回傳 None。避免教材列出的同號和／異號差溢位。

# Chapter 03：迴圈不變量、終止性與搜尋成本

## 學習目標

以初始化、維持、終止三步推理迴圈；分析最壞時間成本；從規格設計獨立的測試 oracle。

## 理論與設計理由

lower_bound 的輸入是非遞減排序切片，輸出第一個大於等於 target 的位置；若不存在則回傳長度。這是一個「分界位置」問題，不只是「找到任意相等元素」。若有重複值，兩個規格會產生不同答案。

以半開區間 [lo, hi) 表示尚未排除的搜尋區。保持不變量：0 ≤ lo ≤ hi ≤ len；lo 左側全部小於 target；hi 起及右側全部大於等於 target。起始 lo＝0、hi＝len，兩側都是空集合，所以不變量成立。

當 values[mid] 小於 target，根據排序性質，mid 以前也不可能是分界，因此更新 lo＝mid＋1。否則 mid 仍可能是第一個符合者，更新 hi＝mid，不能寫 mid－1。這裡保留 mid 的方式正是半開區間與不變量一起決定的，不是死背模板。

迴圈的變量 hi－lo 是非負整數，而且每次未終止的迴圈都會嚴格下降，所以終將停止。當 lo＝hi，未確定區間為空，兩側條件合起來便確定 lo 是答案。這提供正確性與終止性的推理。

每次約縮小一半，時間為 O(log n)，額外空間 O(1)。先驗證整個輸入是否排序則需要 O(n)，會改變 API 的總成本；本題把排序列為前置條件。用線性 position 作為測試 oracle 雖較慢，卻提供結構不同的驗證途徑，避免測試只是複製同一段二分搜尋錯誤。

## 推理實驗

用 [1,3,3,7] 與 target＝3 畫表：每一輪列出 lo、hi、mid 與被排除的區間。接著嘗試把 hi＝mid 改成 mid－1，找出空切片、重複值或邊界的反例。

## 實作規格

# Chapter 04：所有權、移動語意與資源生命週期

## 學習目標

區分值與儲存位置；追蹤 move 後的使用權；以 Drop 觀察資源釋放並理解 RAII。

## 理論與設計理由

記憶體模型先用來推理值的有效性，不是猜實際機器組合語言。區域變數、Box、String 與 Vec 具有不同的擁有關係；不能簡化成「所有變數一定在 stack、所有資料一定在 heap」。編譯器可以最佳化配置，語言層的所有權仍必須成立。

String 擁有字串緩衝區；把 String move 給另一個綁定後，原綁定不能再作為擁有者使用。這通常轉移對既有資源的責任，不代表深拷貝字元。clone 則建立另一個擁有的副本，對 String 可能配置與複製資料。Copy 型別可隱式複製，不能把整數與 String 的行為混為一談。

當值需要被釋放時，Rust 會執行相應的 drop 行為。這種把資源管理綁定生命週期的方式稱為 RAII，也可用於檔案與鎖，不只記憶體。擁有者可以移動，釋放責任會隨之移動；不能因為多了一個變數名稱就多釋放一次。對普通區域綁定可用詞法作用域及宣告順序追蹤，但借用有效範圍與 drop 時點不是同一件事。

本章以 Rc<RefCell<Vec<_>>> 保存事件紀錄。Rc 是單執行緒的共享所有權計數，clone Rc 會增加擁有者數量而不複製整個 Vec；RefCell 把借用衝突的檢查移到執行期，違反會 panic。它們是為了觀察實驗使用，不代表避開借用檢查就能免除規則。循環的 Rc 關係也可能讓計數無法歸零，因此 Rust 的記憶體安全不等於完全不會洩漏資源。

# Chapter 05：借用、別名與可變性的限制

## 學習目標

由資料失效問題理解借用規則；用不重疊分割設計 safe API；理解靜態分析的保守性。

## 理論與設計理由

別名表示多個路徑指向同一份資料。只讀別名通常容易推理；當某個路徑能修改或重配資料，其他路徑可能忽然失效。例如 Vec 擴充容量可能移動元素，先前指向元素的參照不能在重配後繼續使用。這不是只有多執行緒才會發生的問題。

在基本 safe 借用模型中，&mut 提供對借用區域的獨占存取，&T 提供共享存取。實際規則還涉及重借用與內部可變性，不能解讀成「整支程式一輩子只能有一個 &mut」。需要判斷的是相關借用是否仍有效、是否可能重疊；編譯器通常可在最後一次使用後結束借用。

編譯器無法從每個任意索引計算推知兩個位置必然不同，因此即使程式設計者知道 i != j，直接連續索引可能仍被拒絕。split_at_mut 把切片安全地分成不重疊兩部分，讓這個事實出現在型別與 API 結構裡。這是「重新表達證據」，不是與編譯器比誰聰明。

two_mut 的契約必須說清楚：相同索引回傳 None，越界也回傳 None；成功時兩個回傳參照的順序對應 i、j，而不是排序後索引的順序。若忽略這項介面語意，程式可能完全沒有記憶體錯誤卻仍然算錯。safe Rust 只能排除某些類型的錯誤，無法替你保證商業規格或物理意義。

## 推理實驗

這段程式的問題不是索引超界，而是同時活躍的可變借用：

```compile_fail

let y = &mut values[1];

```

改用 split_at_mut 後，在紙上標出兩個區域的邊界。

# Chapter 06：生命週期是關係，不是延長存活的咒語

## 學習目標

從函式簽名推論參照來源；避免過度綁定無關輸入；設計不配置字串的查詢函式。

## 理論與設計理由

回傳 &str 代表回傳某段現存文字的檢視。呼叫者必須知道這段檢視依賴誰仍然有效。生命週期參數表達這種關係，不會讓區域變數多活一秒，也不會配置新字串。若函式創造區域 String 然後回傳它的參照，補上任何名字的 'a 都無法使該 String 在函式結束後繼續存在。

field 的輸出來自 line，不來自 key，所以簽名使用 line: &'a str 與 Option<&'a str>，key 只需要在比較時有效。若把 key 也綁到同一個 'a，可能不必要地縮短呼叫者能使用輸出的範圍。當參數很多時，精確的生命週期關係也是 API 文件的一部分。

「零複製」在本題指不為回傳欄位額外配置與複製文字，不代表整個作業完全沒有讀取成本。split、trim 與相等比較仍需檢查字元或位元組，掃描輸入的時間為 O(n)。UTF-8 字串不能任意以整數索引當成第幾個字；中文可能佔多個位元組。本題讓字串 API 管理合法邊界，不以猜測的位元組長度切片。

缺少欄位與存在但空值也應區別：None 表示沒有匹配欄位，Some("") 表示欄位存在且值為空。這種資料建模讓呼叫者能做正確決策，而不是以空字串同時表示所有狀態。

# Chapter 07：資料建模、型別不變量與模組邊界

## 學習目標

以建構函式維護有效狀態；理解欄位可見性與封裝限制；區分型別安全與領域正確性。

## 理論與設計理由

若任意 f64 都能當作時間，呼叫每個計算函式時就要重新問它是否為零、負數、NaN 或無限大。建立 Seconds 新型別，並只透過驗證過的建構函式產生值，可以把「有限正數」變成該型別的不變量。後續函式接收 Seconds 時，便能依賴這個約定。

這個設計仍需封裝。若把內部欄位公開，使用者可以直接造出 Seconds(-1.0)，建構函式的保證就被繞過。Rust 的私有欄位以模組為界，同一個模組內仍能直接存取；要對外建立可靠 API，型別與修改途徑應放進受控模組，不能只在檔案開頭加 private 的想像。

# Chapter 08：Trait、泛型與分派策略

## 學習目標

由需要的行為定義抽象；比較靜態與動態分派；理解抽象介面不會自動保證語意。

## 理論與設計理由

泛型函式不必知道每個具體型別的全部細節，只要求型別符合必要的 trait。這像是函式契約的另一層：需要一個 magnitude 方法，不需要繼承某個共同資料結構。Trait 描述可使用的操作，方法的數學意義仍由文件與實作遵守。

以 T: Measured 接受 &[T]，同一個切片的元素都是同一個具體 T。編譯器通常藉由單態化產生對應具體型別的版本，讓呼叫有機會被內聯與最佳化，代價可能是編譯時間與程式碼大小增加。靜態分派不是保證所有情境都比較快。

&dyn Measured 是對 trait object 的借用，可讓一個 &[&dyn Measured] 同時引用不同的具體型別。動態分派透過執行期方法表選擇實作，帶來間接呼叫與最佳化限制；&dyn 本身不要求 heap 配置，只有選擇 Box 等擁有方式時才涉及相應配置。不是所有 trait 都符合動態相容條件，例如方法含某些泛型形式會影響可用性。

本練習故意讓 Distance 與 Time 都實作 magnitude，觀察型別系統可以接受「不同物理量的數值相加」，卻不代表這是有效物理運算。Trait 合約如果只保證能取得數值，就不能推導可相加。進一步的單位型別設計要避免這種語意混淆，而非把順利編譯當成領域正確。

## 推理實驗

寫出泛型版本與 dyn 版本的資料圖，標示哪些物件借用原值、是否需要配置。解釋為什麼 &[Distance] 不能直接塞入 Time，以及 dyn 能接受它仍不代表相加有物理意義。

## 實作規格

# Chapter 09：迭代器、惰性求值與配置成本

## 學習目標

追蹤 adapter 與 consumer 的求值時機；分析時間與輸出空間；避免只看語法簡潔度判斷效能。

## 理論與設計理由

迭代器提供逐步產生元素的協定。map、filter 等 adapter 通常只建立描述計算的迭代器，不會立刻處理所有元素；collect、sum 或實際呼叫 next 才驅動計算。惰性使 take 有機會及早停止，但 adapter 的順序也會改變語意。

「先過濾正數再取前 k 個」與「先取前 k 個再過濾」不是同一個問題。給定 [-1,2,3]，前者取兩個正數得到 [2,3]，後者只在前兩項內找到 [2]。把函數組合寫得漂亮卻改變規格，是常見錯誤。

平方前應把 i32 擴大為 i64。i32 的正最大值平方可由 i64 表示；若先在 i32 做乘法再轉型，錯誤已經發生。這是資料流中運算位置的重要性，不能只看最後回傳型別。

惰性管線不代表零配置：collect::<Vec<_>>() 需要保存結果。輸入最多掃描 n 項，輸出 m 項的空間為 O(m)，其中 m ≤ min(k,n)。如果正數很稀少，即使只取少量結果仍可能掃描整份輸入。這裡沒有額外中間 Vec，但最後的輸出仍占空間。

所謂零成本抽象，是讓高層表達有機會最佳化成接近手寫迴圈的機器碼，不是說所有 iterator 管線自動最快。效能實驗需要 release 模式、合理資料分布、避免量到編譯與終端機輸出，也要先保證兩版本做同樣工作。本章只分析成本與觀察求值，不宣稱量測出加速。

## 推理實驗

# Chapter 10：錯誤作為資料與純核心／副作用邊界

## 學習目標

設計可區分原因的錯誤型別；理解 ? 的傳遞規則；把解析、計算與 I/O 責任分開。

## 理論與設計理由

panic 適合指出某些程式內部預期被破壞的情況，不適合把每個使用者輸入錯誤都當成程式崩潰。Result 把成功與失敗列為介面的一部分，呼叫者可決定重試、記錄、顯示或終止。比起 Err("錯了")，具名 enum 可以穩定區分欄位數、轉換、非有限值與領域限制。

? 不是忽略錯誤。對 Result 而言，它在成功時取得內容，失敗時提早回傳；必要時透過相容的 From 轉換錯誤型別。map_err 則明確改寫錯誤表示。責任仍存在，只是傳遞路徑比層層 match 短。

把 parse_record(&str) 寫成不直接讀檔、不印訊息的函式，讓同一個邏輯能被測試、終端機或其他 UI 使用。最外層負責取得文字與顯示錯誤，內層負責判斷文字是否符合資料規格。這種邊界讓測試可以固定輸入，不需模擬使用者鍵盤或檔案權限。

錯誤分類也代表驗證順序。本題先檢查兩欄，再轉數字，再檢查有限性，最後檢查正時間。若某行同時違反多個條件，回傳先遇到的錯誤。API 應交代這點，測試才不會把實作細節誤當隨機結果。本練習只是兩欄逗號分隔格式，不支援引號內逗號等完整 CSV 規則；應明確說出格式範圍。

## 推理實驗

# Chapter 11：並行中的所有權與可重現結果

## 學習目標

區分資料競爭與其他競態；用作用域執行緒借用輸入；分析並行工作的成本與限制。

## 理論與設計理由

並行讓不同工作在時間上交錯或同時執行；它不會自動讓程式更快。建立執行緒、排程與等待都有成本，少量數字的加總常常由單執行緒較有效率。先確定工作可分割，再考慮資料量是否足以攤平開銷。

資料競爭涉及未同步的重疊記憶體存取，其中至少一方寫入。Rust 透過借用、Send、Sync 等機制，限制安全程式中的不安全共享。Send 描述值能否跨執行緒轉移；Sync 描述共享參照能否安全跨執行緒使用。它們不表示任意業務操作已經有正確的先後順序，也不防止死結或所有邏輯競態。

本題把輸入切成兩個共享唯讀切片，各自求和後合併。thread::scope 讓子執行緒可借用外層區域資料，並保證在作用域結束前完成等待；這與一般 thread::spawn 可能要求捕獲資料符合 'static 的情況不同。move closure 可以移動參照本身，不等於複製或取得整份底層陣列的所有權。

加總先轉成 i64，避免 i32 小範圍溢位。本練習的契約限定輸入長度不超過一百萬筆 i32，因此數學總和可由 i64 表示；不應把這個實作描述為能對任意長度永不溢位的通用函式。整數在可表示範圍內分組不改變結果；若換成浮點數，不同分組可能導致捨入差異。

Rc 不具備跨執行緒所需的執行緒安全計數；Arc 提供原子計數，但共享可變資料仍需要 Mutex、RwLock 或其他適當同步。不能只把 Rc 改名成 Arc 就宣稱整個設計安全且正確。

```

## 理論與設計理由

專案的輸入是一段 UTF-8 文字，每行恰好是「有號位移,正秒數」，沒有標題列、不接受空白行，不支援帶引號的完整 CSV。先明確限制格式，才能判定哪個輸入應成功。檔案為空與某一行格式錯誤是不同的失敗情況，錯誤需要保留原始的一起算行號。

分析核心回傳 Summary，包含筆數、總位移與總時間；平均速度是總位移／總時間。分段速度直接平均在時間不同時沒有這個意義。總路程／總時間才是平均速率，單看每筆有號位移也未必知道該段實際路程，因此本專案不冒稱計算完整路程。

每筆數值有限不保證累加結果仍有限，所以要檢查累加溢位。總位移與時間都有限也不保證最後相除為有限，例如極小正時間，因此還需要檢查最終比值。這些檢查排除非有限結果，但不消除一般浮點捨入與消去誤差；科學用途還需要誤差預算或更進一步的加總策略。

核心函式 analyze 不讀檔也不印字，CLI 負責路徑、stdin、stdout、stderr 與退出碼。當錯誤時輸出到 stderr 並回傳非零退出碼，其他程式才能以管線或自動化判斷成功與失敗。參考版本一次讀入全部文字，時間 O(n)，儲存原文為 O(n)，核心逐行累加狀態為 O(1)；它不是串流讀檔實作。

設計說明應解釋為何選擇嚴格格式、為何遇錯即停、為何保留行號，以及是否支援部分成功。這些是介面政策，不是 Rust 唯一正解。比較替代設計後，選擇與需求一致的方案，才是本課程最終要驗收的能力。

cargo run -p rust-advanced-course --example lab12 -- advanced/data/motion.csv
```

## 實作規格

完成 analyze，保留已提供的 CLI 與測試。空檔回傳 Empty；行格式／數值錯誤回傳含行號的 Line；累加或最後比值非有限回傳 Overflow。接受 CRLF 及一般尾端換行，拒絕真正的空白資料行。

起始檔：`examples/lab12.rs`。先閱讀測試，再修改函式。

```sh
cargo test -p rust-advanced-course --example lab12
cargo run -p rust-advanced-course --example lab12
```

起始程式中的 `todo!()` 可編譯，但執行或相關測試會 panic，這是刻意保留的待完成工作；通過編譯不代表通過規格。

## 終端機自動驗收

完成作答後執行：

```sh
cargo run -p rust-advanced-course -- run 12
```

此命令自動編譯學生程式並執行獨立的函式契約測試，不需手動輸入測試值。第十二章另有多組標準輸入／輸出與退出碼案例。驗收在暫存檔附加測試，不會修改你的程式或使用參考答案替換作答；失敗退出碼為１。起始程式中的 `todo!()` 會使驗收失敗。

需要自行輸入、觀察輸出或附加檔案路徑時，使用 `cargo run -p rust-advanced-course -- manual 12`；原本的 `cargo test -p rust-advanced-course --example lab12` 仍可執行檔案內測試。自動驗收有逾時限制，但不是執行不受信任程式的安全沙盒；有限測試也無法代替設計推理、複雜度分析與個別口頭說明。
