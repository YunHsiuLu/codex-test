# 單元５：函式、遞迴、契約與早期測試

## 學習成果與先備

本單元要把一段程式拆成有明確輸入、輸出與責任的函式。
完成後，你應能追蹤一般與遞迴呼叫，區分回傳與印字，以簡單斷言檢查契約，並解釋遞迴為何終止及如何逐層返回。
先備是變數、數值運算、條件與迴圈。

在 beginner 執行 `cargo run -- lesson 5` 閱讀。
本課示範時間換算、時間組合與遞迴點數累加；各題的完整實作由學習者完成。

從本單元開始，起始程式中的 `todo!("說明")` 是尚未實作的標記：它可以編譯，但執行到該處會觸發 panic。請用自己的實作替換整個 todo! 表達式，而不是只修改括號中的文字。起始驗收失敗代表工作尚未完成，不是工具安裝壞掉。

## 5.1 函式是可重複使用的計算介面

把相同公式複製到多個地方，修改時很容易只改一份。
函式把計算規則集中在一處，其他位置透過名稱與參數使用它。
一個好的函式名稱，也讓讀者先理解意圖，再決定是否深入讀公式。

```rust
fn minutes_to_seconds(minutes: i64) -> i64 {
    minutes * 60
}

fn main() {
    let first = minutes_to_seconds(2);
    let second = minutes_to_seconds(5);
    println!("first={first}, second={second}");
}
```

fn 開始函式定義；minutes 是參數名稱，i64 是它接收的型別。
箭頭右邊的 i64 指定回傳型別。
呼叫時的２與５是引數，分別被交給這次呼叫中的 minutes。

| 呼叫 | 本次 minutes | 計算 | 回到呼叫處的值 |
| --- | --- | --- | --- |
| minutes_to_seconds(2) | 2 | 2 × 60 | 120 |
| minutes_to_seconds(5) | 5 | 5 × 60 | 300 |

每次呼叫的區域資料分開存在，第二次呼叫不會偷偷沿用第一次的 minutes。
函式本體在呼叫時才執行，定義寫在 main 前後都不表示它會先自行跑一次。

## 5.2 回傳值與輸出文字不同

上面的函式交回數值，main 才決定要印、再計算或保存。
這種分工讓函式也能被測試、檔案工具或其他介面使用，不必知道數字最初來自鍵盤還是固定資料。

下列程式是刻意的編譯錯誤：

```compile_fail
fn minutes_to_seconds(minutes: i64) -> i64 {
    println!("{}", minutes * 60);
}
fn main() {}
```

println! 把文字寫到輸出，不會把那個整數作為 i64 回傳。
函式宣告要交回 i64，實際卻沒有提供它，因此不能通過型別檢查。
看見終端機顯示１２０，不等於呼叫者已拿到整數１２０。

## 5.3 最後表達式與提早 return

Rust 可使用函式本體最後一個不加分號的表達式作為回傳值。
`minutes * 60` 與 `return minutes * 60;` 可以表達相同回傳，但後者也可在函式中間提早離開。

```rust
fn shipping_minutes(stops: i64) -> i64 {
    if stops == 0 {
        return 0;
    }
    let travel = stops * 8;
    let loading = 5;
    travel + loading
}

fn main() {
    println!("no stops: {}", shipping_minutes(0));
    println!("three stops: {}", shipping_minutes(3));
}
```

本示範假設 stops 是小型非負整數。
當 stops＝０，return 直接結束函式，不會再加入裝載時間。
當 stops＝３，先計算２４分鐘行程，再回傳２９。

若在最後的 `travel + loading` 後加分號，就把它變成被執行後捨棄結果的敘述。
這不是所有分號都不能用，而是要分清楚哪一個位置負責交出值。

## 5.4 區域作用域與呼叫者的名字

呼叫者可以使用與函式參數不同的變數名稱。
例如 main 的 duration 傳入 minutes_to_seconds 後，函式內仍以 minutes 稱呼本次接收到的值。
對 i64 參數的計算不會自動修改呼叫者的原變數。

函式內宣告的 travel、loading 等名字，只在相應作用域有效。
不要為了跨函式共享某個值就隨意建立全域變數；先問它能否作為參數或回傳值明確傳遞。
這讓資料來源更清楚，也讓同一個函式容易用不同資料測試。

## 5.5 以小函式組合較大的工作

```rust
fn minutes_to_seconds(minutes: i64) -> i64 {
    minutes * 60
}

fn timer_value(hours: i64, extra_minutes: i64) -> i64 {
    let whole_minutes = hours * 60 + extra_minutes;
    minutes_to_seconds(whole_minutes)
}

fn main() {
    println!("one hour five minutes={}", timer_value(1, 5));
    println!("three minutes={}", timer_value(0, 3));
}
```

呼叫關係是 main → timer_value → minutes_to_seconds，再依序回到呼叫處。
timer_value 不重新複製「分鐘乘６０」的公式，而是重用已有介面。
如果測試指出換算錯誤，可以分別檢查組合與底層換算，縮小問題範圍。

拆函式不是把每一行都換成一個名字。
當一段工作有清楚意義、值得重用或需要獨立測試時，拆出來才更有幫助。
函式過度依賴外部隱藏狀態，也會削弱這些好處。

## 5.6 前置條件、後置條件與 assert!

前置條件描述呼叫時應成立的要求，後置條件描述成功回傳後應成立的關係。
例如以下示範只接受非負分鐘與０～５９的秒欄位，回傳合成的總秒數。

在使用前先認識兩個檢查工具：assert!(條件, "訊息") 要求布林條件為 true，否則觸發 panic；assert_eq!(實際值, 預期值) 要求兩個值相等，否則觸發 panic 並顯示差異。
驚嘆號表示巨集，和 println! 相同；完整說明接在示範後面。

```rust
fn clock_seconds(minutes: i64, seconds: i64) -> i64 {
    assert!(minutes >= 0, "minutes must be nonnegative");
    assert!(seconds >= 0 && seconds < 60, "seconds must be in 0..60");
    minutes * 60 + seconds
}

fn main() {
    assert_eq!(clock_seconds(2, 15), 135);
    assert_eq!(clock_seconds(0, 0), 0);
    println!("clock fields checked");
}
```

assert! 接收 bool，成立就繼續，不成立會觸發 panic。
第二個參數是失敗訊息，可幫助指出哪個要求被破壞。
assert_eq! 比較兩個值是否相等，不等時會顯示兩邊資訊。
名稱尾端的驚嘆號表示巨集，與條件前的布林否定 ! 不同。

這裡的數值範圍還假設合成結果可由 i64 表示，不能因為加了兩個 assert 就宣稱任意大數都不會溢位。
若規格還包含更大範圍，必須另外設計表示法或檢查方式。
契約的意義是把要求說清楚，不是宣稱幾行檢查能解決所有情況。

## 5.7 panic 與可預期的使用者錯誤

assert 失敗會使目前執行緒 panic；未被捕捉的主執行緒 panic 會讓這次程式失敗。
它不同於編譯錯誤，因為程式可以編譯，但執行到違反要求的路徑才發生。
一般 assert! 在 debug 與 release 都會檢查，不能假設最佳化後會消失。

使用者打錯資料是可預期事件，通常應給外層選擇如何處理，而不是一律 panic。
單元１０會以 Result 表達這類正常的失敗路徑。
本課先用 assertion 練習內部契約與測試，不要求自己捕捉 panic，也不需要先學閉包或 catch_unwind。

## 5.8 最小測試框架：讓工具自動呼叫檢查

```rust
fn minutes_to_seconds(minutes: i64) -> i64 { minutes * 60 }
fn clock_seconds(minutes: i64, seconds: i64) -> i64 {
    assert!(minutes >= 0);
    assert!(seconds >= 0 && seconds < 60);
    minutes * 60 + seconds
}
fn main() {}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn two_minutes() { assert_eq!(minutes_to_seconds(2), 120); }
    #[test]
    fn no_time() { assert_eq!(minutes_to_seconds(0), 0); }
    #[test]
    #[should_panic]
    fn invalid_seconds_are_rejected() { clock_seconds(1, 60); }
}
```

#[test] 請測試工具執行下一個函式。
#[cfg(test)] 讓模組只在測試設定下編譯；mod tests 組織測試，use super::* 引入上層函式名稱。
這是先提供的固定框架，不代表你已完整學過模組系統；單元１１、１２會深化。

#[should_panic] 表示這個案例預期觸發 panic，若函式安靜接受錯誤資料，測試反而失敗。
正常案例不要加這個標記，否則可能把原本不應發生的失敗當成成功。
此例不使用 catch_unwind，不需要把新概念一次塞進來。

## 5.9 先看到紅燈，再確認修正成綠燈

在上面的換算函式中，暫時把乘６０改成乘１０，再執行測試。
two_minutes 仍要求１２０，但錯誤版本得到２０，因此該測試應 FAILED，這是紅燈。
恢復正確公式後再跑，正常案例與預期 panic 案例都應通過，得到綠燈。

預期值要根據規格與手算決定，不能只改成目前錯誤輸出的２０來追求通過。
後續可以加入不同資料，確認測試不只對某一個巧合輸入有效。
單元１１會讓你專門設計測試，並用多個故障版本檢查辨識能力。

## 5.10 遞迴：函式也能呼叫自己

函式可以呼叫另一個函式，也可以呼叫自己。後者稱為遞迴（recursion，也常寫成遞回）。每次呼叫都有自己的參數與區域變數，沿用前面的一般函式模型，並沒有讓某一個全域變數自動倒數。

先把一個大問題描述成「較小的同類問題，再加上本層要完成的工作」。例如第n層有n個點，前n層的點數可表達為：本層點數n，加上前n−1層的點數。沒有任何層時，點數為０。

```rust
fn layer_points(level: u32) -> u32 {
    assert!(level <= 10, "示範只處理小型層數");
    if level == 0 {
        return 0;
    }
    let smaller = layer_points(level - 1);
    level + smaller
}

fn main() {
    let answer = layer_points(3);
    assert_eq!(answer, 6);
    println!("{answer}");
}
```

這個完整示範印出６。`u32`是無號３２位元整數，這裡用來表達非負層數；示範先限制level不超過１０，避免把學習呼叫流程變成巨大資料的數值或堆疊問題。

遞迴有兩個必要部分：

- 基底情況（base case）：level為０時直接回傳，不再呼叫自己。
- 遞迴步驟：其他情況把level減一，先取得較小問題的答案，再加上本層點數。

只有「呼叫自己」還不夠，必須知道何時停止，以及每次為什麼更接近停止。

## 5.11 呼叫堆疊：等待的是不同次呼叫

執行`layer_points(3)`時，第一層不能立刻求出結果，必須先等待`layer_points(2)`。第二層又等待下一層，直到基底情況有確定答案。

```text
呼叫深入：
layer_points(3)  等待 3 + layer_points(2)
  layer_points(2)  等待 2 + layer_points(1)
    layer_points(1)  等待 1 + layer_points(0)
      layer_points(0)  直接回傳 0

逐層返回：
layer_points(1)  取得 0，回傳 1
layer_points(2)  取得 1，回傳 3
layer_points(3)  取得 3，回傳 6
main             取得 6，才決定如何顯示
```

這種「後進入的呼叫先完成」可以用呼叫堆疊（call stack）理解。每層的執行資訊稱為一個呼叫框架；本課用它記錄參數、等待回到哪裡，以及尚未完成的工作。這是推理執行順序的模型，不承諾編譯後每層一定配置固定大小或完全相同的機器指令。

| 當次呼叫 | 自己的level | smaller何時確定 | 回傳值 |
| --- | --- | --- | --- |
| 最深的呼叫 | 0 | 不需要smaller | 0 |
| 等待上一列的呼叫 | 1 | 子呼叫回傳0後 | 1 |
| 再上一層 | 2 | 子呼叫回傳1後 | 3 |
| 最外層 | 3 | 子呼叫回傳3後 | 6 |

同名的level沒有被所有呼叫共用；最外層等待時，自己的level仍是３。`return`只結束目前這次呼叫，把控制權交回上一層，不會一次結束所有尚在等待的呼叫。

## 5.12 終止理由、傳回結果與常見失誤

用遞迴解題前，先回答三個問題：

１．哪個輸入可以直接知道答案？

２．下一次呼叫的輸入如何改變，而且確實更接近基底情況？

３．下一層回傳後，本層還要做什麼，最後如何交回結果？

上面的終止理由是：level為非負整數；非基底情況每次減一；不可能一直減少卻永遠不碰到０。必須先判斷０，再計算level−1；無號整數不能拿負數當停止標記。

以下只是錯誤方向的說明，不是要實際執行的程式：

- 每次都用相同的level呼叫自己：問題沒有縮小。
- 先呼叫自己，再檢查是不是０：還沒走到檢查就可能不斷深入。
- 子呼叫算出答案，但本層只印字或捨棄結果：呼叫者沒有取得宣告要回傳的數值。
- 以為看見一層return就代表整個程式結束：其他等待中的呼叫仍要接收結果並繼續。

即使數學上會終止，過深的遞迴仍可能超出有限的呼叫堆疊空間。不能把「會到達基底情況」直接等同於「任意大輸入都能安全執行」，也不要靠實際觸發堆疊溢位來找正常的停止位置。

## 5.13 與迴圈比較：選擇如何表達重複

```rust
fn layer_points_loop(level: u32) -> u32 {
    assert!(level <= 10);
    let mut total = 0;
    for current in 1..=level {
        total += current;
    }
    total
}

fn main() {
    assert_eq!(layer_points_loop(3), 6);
    println!("{}", layer_points_loop(3));
}
```

這個迴圈版對相同示範資料得到相同答案。遞迴版把尚未完成的加法留在不同呼叫中；迴圈版把目前總和放在一個累加器中。

兩種直接實作的主要工作都隨層數線性增加，可記為O(n)時間。依上面的呼叫模型，遞迴版需要隨深度增加的等待資訊，為O(n)額外空間；迴圈版只保留固定數量的計數與累加變數，為O(1)額外空間。這些是對演算法的推理，不是這段受限於１０的示範已做效能測量。

本例在子呼叫返回後還要相加，不是尾呼叫。即使另一種寫法把遞迴呼叫放在最後，也不能假設工具鏈一定消除所有呼叫框架；本課的正確性與輸入限制不依賴這種最佳化。

遞迴適合直接表達某些問題的結構，並不保證比較快或比較省記憶體。現在先能把一個例子逐層追完，再討論更複雜的分治或樹狀問題。

## 5.14 兩份遞迴實作的數學模型

5-4以階乘練習「先等子問題，再做本層乘法」。n!表示從１乘到n；定義０!＝１。題目以u32接收n、以u64回傳答案，限定n不超過２０；u64是無號６４位元整數，不代表可以保存任意大的整數。超出題目範圍要先以assert拒絕，不要等乘法溢位或深入大量呼叫才失敗。具體介面與兩組範例見作業頁。

5-5以歐幾里得演算法練習「把一組參數轉成較小的同類問題」。當b大於０，可以把a寫成`a = q * b + r`，其中`r = a % b`。a與b的共同因數也會整除r；反過來，b與r的共同因數也會整除a。因此最大公因數可改由b與r求得，而r嚴格小於原本的b，形成終止的進展。

當b為０時直接回傳a，不再計算`a % b`。若兩者都為０，這份作業約定回傳０；這是本題的API約定，不是聲稱數論中０與０有一般意義下的最大公因數。需要在介面先寫清楚這種情況，才不會讓測試或呼叫者各自猜測。

兩題都要求練習遞迴。自動驗收檢查函式結果與契約；是否真的採用遞迴，以及能否說明終止和返回過程，另以程式閱讀與呼叫追蹤檢查，不靠搜尋原始碼中的某個字樣假裝判定設計品質。

## 常見錯誤與自我檢核

- 只印結果卻宣告要回傳數值：輸出與回傳責任不同。
- 最後表達式多了分號：函式沒有交出預期型別。
- 所有函式都重新抄同一公式：失去集中修改與獨立驗證的優點。
- 參數型別正確就假設數值有效：還要對照契約。
- 用 should_panic 掩蓋普通案例失敗：測試的預期方向寫錯。
- 遞迴只有停止條件卻沒有進展：不能保證到達停止條件。
- 把不同呼叫的同名參數當成同一變數：無法正確追蹤返回過程。

問題一：參數名稱必須與呼叫者變數同名嗎？
答案：不必；引數的值依參數位置與型別交給函式。

問題二：回傳值能否先做別的計算而不印出？
答案：可以；輸出是呼叫者決定的一種用途，不是數值回傳本身。

問題三：為什麼契約與測試都需要？
答案：契約說明允許與要求，測試對選定資料提供可重現證據，兩者不能彼此取代。

問題四：layer_points最深一層回傳０，為何最外層不是直接得到０？
答案：每層都會在子呼叫回來後完成自己的加法，依序把新結果交回上一層。

問題五：有基底情況就一定會停止嗎？
答案：不一定。輸入轉換必須保證朝基底情況前進；參數不變的遞迴仍可能一直深入。

問題六：b為０時，為何必須先返回，而不是先算a % b？
答案：餘數運算的除數不能為０；基底情況的順序也是正確性的一部分。

- [５－２：把數值限制在範圍內](../exercises/5-2.md)：回傳限制後的i64，不要求在函式裡印字；題目列出上下限、端點與預期回傳，另附可自行放進main的觀察示範。
- [５－３：面積與費用的函式重用](../exercises/5-3.md)。
- [５－４：遞迴階乘](../exercises/5-4.md)：練習基底情況、返回後乘法與表示範圍。
- [５－５：遞迴最大公因數](../exercises/5-5.md)：練習參數轉換、餘數與終止理由。

以 `cargo run -- lesson 5-1` 讀題，`cargo run -- run 5-1` 驗收。
作業中的函式有固定名稱與型別，請遵守介面，計算細節自己設計。
原生 cargo test 與課程驗收的確切用法依作業頁指定來源操作。

官方閱讀：[函式](https://doc.rust-lang.org/book/ch03-03-how-functions-work.html)、[測試](https://doc.rust-lang.org/book/ch11-01-writing-tests.html)、[assert!](https://doc.rust-lang.org/std/macro.assert.html)。

遞迴相關延伸：[函式呼叫表達式](https://doc.rust-lang.org/reference/expressions/call-expr.html)、[u64的表示範圍](https://doc.rust-lang.org/std/primitive.u64.html)、[執行緒堆疊大小](https://doc.rust-lang.org/std/thread/struct.Builder.html#method.stack_size)。最後一項供理解堆疊是有限資源，不要求此時建立執行緒或調整堆疊來完成作業。
